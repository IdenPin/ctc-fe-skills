# 发布与回滚

## 现状边界

当前 `deploy/deploy.mjs` 先清空远端目标目录，再解压 Artifact。若传输中断或解压失败，可能留下不完整目录；脚本本身没有版本保留、原子切换或回滚命令。GitLab Artifact 有期限，也不能代替服务器端的已知可用版本。不要把当前脚本描述成具备自动回滚。

## 推荐发布模型

- 每次以 commit SHA 建立独立 release 目录，例如 `releases/<sha>`，先完整上传和校验。
- 静态站点通过 `current` 符号链接或等效原子指针指向活动 release；确认新版本文件齐全后再切换指针。
- 保留至少一个上一成功版本，并清理超出约定数量/保留期的旧版本。确保 release 与链接位于同一文件系统，切换不会跨盘复制。
- 记录环境、commit SHA、Artifact ID、部署时间、当前 release 和前一 release。Artifact 留存策略应覆盖团队需要的回滚周期。

## 回滚步骤

1. 暂停同环境后续部署，确认故障影响和最近一次已知可用 commit。
2. 优先将活动指针切回保留的上一 release；如果无服务器版本目录，则从 GitLab 取回对应 commit 的原始 Artifact，用相同环境配置重新发布。避免在回滚时从最新分支重建。
3. 验证首页、静态资源、API 登录/健康检查和关键功能；确认 CDN/Nginx 缓存没有继续服务旧配置。
4. 通知团队实际回退的 commit、环境、故障现象和流水线链接，并记录后续修复任务。

生产发布规范完成前，应实现并验证可回退路径。若当前部署实现尚未具备它，明确告知用户，需要先补充备份/原子切换，再承诺生产回滚。
