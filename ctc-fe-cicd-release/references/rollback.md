# 发布与回滚

## 现状边界

`self-monitor-system` 当前的 `deploy/deploy.mjs` 先清空远端目标目录，再解压 Artifact。若传输中断或解压失败，可能留下不完整目录；更严重的是，清空目录会直接破坏在途请求，导致仍在使用旧页面的用户在访问懒加载 chunk 资源时遭遇 404（引发前端 ChunkLoadError 或白屏）。同时，该项目脚本本身没有版本保留、原子切换或回滚命令。GitLab Artifact 有期限，也不能代替服务器端的已知可用版本。不要把这项项目现状泛化到其他仓库；每次都要查看目标仓库部署脚本，并按实现说明回滚次数、目标版本和失败恢复方式。

## 推荐发布模型

- 每次以 commit SHA 建立独立 release 目录，例如 `releases/<sha>`，先完整上传和校验。
- 静态站点通过 `current` 符号链接或等效原子指针指向活动 release；确认新版本文件齐全后再切换指针。
- 远端 Web 服务器（如 Nginx）配置需放行符号链接（`disable_symlinks off;` 或允许同属主软链），避免切换后直接遭遇 403 Forbidden；并关注 `open_file_cache` 刷新窗口。
- 保留近期历史版本平滑过渡：清理旧版本时避免只按单次计数硬删，建议采用“保留最近 5 个版本且不删除设定时间（如 24 小时或 3 天）内版本”的双重策略，配合前端应用层 `vite:preloadError` 错误重试与刷新机制，确保在线长停留用户不因高频发版遭遇旧 hash 资源 404。确保 release 与链接位于同一文件系统，切换不会跨盘复制。
- 记录环境、commit SHA、Artifact ID、部署时间、当前 release 和前一 release。Artifact 留存策略应覆盖团队需要的回滚周期。

## 回滚步骤

1. 暂停同环境后续部署，确认故障影响和最近一次已知可用 commit。
2. 优先将活动指针切回保留的上一 release；如果无服务器版本目录，则从 GitLab 取回对应 commit 的原始 Artifact，用相同环境配置重新发布。避免在回滚时从最新分支重建。
3. 验证首页、静态资源、API 登录/健康检查和关键功能；确认 CDN/Nginx 缓存没有继续服务旧配置。
4. 通知团队实际回退的 commit、环境、故障现象和流水线链接，并记录后续修复任务。

生产发布规范完成前，应实现并验证可回退路径。若当前部署实现尚未具备它，明确告知用户，需要先补充备份/原子切换，再承诺生产回滚。
