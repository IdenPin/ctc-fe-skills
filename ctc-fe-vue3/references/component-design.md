# 组件职责与封装契约

## 拆分决策

先用一句话描述组件的主要职责，再判断内部交互是否独立变化。布局标签数量、出现多个 ref、只有一个调用方，都不能单独决定是否拆分。

| 情况 | 处理要求 |
| --- | --- |
| 单一交互，模板、局部状态与事件紧密相关 | 保留在组件内，不机械创建配套文件。 |
| 多个交互区块拥有独立输入、事件或维护原因 | MUST 拆为私有子组件；明确各区块的输入与输出。 |
| 多个组件复用有状态逻辑，或存在可独立描述的复杂状态流程 | SHOULD 抽 composable；保留唯一状态所有者。单个调用方也可以抽取。 |
| 无响应式状态的格式化、校验、数据转换 | 保持普通函数；是否单独成文件由复杂度和实际使用决定。 |
| 单一职责的声明式模板或样式触及体积限制 | 按展示结构、可独立维护的配置或样式职责整理，并满足结构规范上限。 |

拆分前明确每个拟新增组件的职责、props、emits 与状态所有者。若子组件仅转发全部参数、没有独立展示或交互职责，应重新评估边界。禁止只将整段脚本搬入 composable 后声称已完成职责拆分。

入口和路由页面默认负责数据协调与组件装配，子组件承接独立交互。一个简单页面可以保持单文件；复杂页面的容器仍可拥有查询条件、当前选择等协调状态，无需为了让入口“只剩标签”继续增加包装层。

## 状态所有权与组件通信

- MUST 对实际使用的 props、emits、slots 和公开方法建立类型契约；不生成空的声明或占位事件。
- MUST 视 props 及传入对象为只读。子组件通过事件提出修改，由所有者更新；不要依赖嵌套对象修改实现隐式双向通信。
- SHOULD 优先使用 props、emits 和 slots；只有真实双向绑定使用 `defineModel`，并核对项目 Vue 与工具版本是否支持。
- 表单草稿、展开状态等局部状态由负责交互的组件持有。多个区块需要协同时，由最近共同所有者协调，不互相读取组件内部状态。
- 使用 provide/inject 时，MUST 通过 `InjectionKey` 定义类型，并明确缺少 provider 时的处理。共享状态由 provider 持有，消费者通过明确动作修改；禁止用模块级可变对象代替实例上下文。
- `defineExpose` 仅公开确需命令式调用的稳定方法。不要暴露整份内部 refs，或把父组件读取子组件私有字段作为主数据流。

## 包装组件与透传

- 包装第三方组件时，MUST 明确 props、emits、slots、attrs 和必要公开方法的支持范围，仅转发有意支持的能力。
- 调整根节点、增加外壳或变为多根节点时，检查 `class`、`style`、原生属性和未声明监听器应落到哪个元素；必要时使用 `inheritAttrs: false` 和显式绑定。
- 已在 emits 中声明的事件由组件主动发出；避免同时透传和重发造成重复响应。
- 保持 `v-model` 的输入与更新事件一致；异步校验或内部草稿不能隐式修改父值。表单明确何时初始化、重置和提交，避免 props 更新覆盖尚未提交的编辑。
- slots 是真实扩展需求时才公开；不要为未来可能的定制生成大量空 slot。

## 拆分后的检查

Review 确认原有公开接口、关键交互和样式作用域仍成立；检查是否有重复状态、双重请求、丢失的事件或属性。目录归属、容量、命名和共享能力提升按 `ctc-fe-structure` 执行，不在本分册另设规则。
